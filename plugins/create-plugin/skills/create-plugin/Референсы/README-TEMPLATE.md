# Универсальная структура README агента

Предложение единого формата для всех сборок. Основа — разбор 36 README из этой папки.

**Читатель README** — сотрудник, который впервые видит агента, а не разработчик. Прочитав документ за 2–3 минуты, он должен понять три вещи: что это за агент, что ему дать, что он сделает. Поэтому в документе нет технических имён и описания внутреннего устройства.

## 1. Структура

Порядок блоков повторяет вопросы пользователя: «что это → что умеет → что ему дать → как начать → как просить → где остановится».

### Обязательные блоки — есть в каждом README

| № | Блок | На какой вопрос отвечает | Что внутри | Объём |
|---|---|---|---|---|
| 1 | **Название** | Кто это? | Название роли, как в карточке агента | 1 строка |
| 2 | **Описание агента** | Для кого он и зачем? | Для кого, какую работу ведёт, с каким итогом | 2–4 предложения |
| 3 | **Что умеет агент** | Какие задачи можно отдать? | Таблица: функция → когда использовать → что получите | 1 строка на функцию |
| 4 | **Какие данные нужны** | Что подготовить? | Откуда агент берёт данные; таблица: функция → нужно → желательно → что будет без них | 1 строка на функцию |
| 5 | **Как работать** | С чего начать? | 3–5 шагов глазами пользователя, включая проверку результата | 3–5 строк |
| 6 | **Примеры запросов** | Как сформулировать? | Живые фразы, минимум по одной на функцию | 3–10 строк |
| 7 | **Границы работы** | Чего не ждать и что остаётся за мной? | Что агент не делает; что решает человек | 2–5 строк |

### Дополнительные блоки — только если выполнено условие

| Блок | Когда нужен | Куда поставить |
|---|---|---|
| **Подготовка перед запуском** | Без настройки агент не работает: нужно наполнить базу знаний, заполнить параметры компании | Перед «Как работать» |
| **Подключения** | Часть функций работает лучше или только с внешней системой | После «Какие данные нужны» |
| **Как агент работает с данными** | Важно разделять факты, расчёты и допущения или есть особые правила при конфликте источников | После «Какие данные нужны» |
| **Рекомендуемые цепочки** | Функции связаны: результат одной служит входом для другой | После «Как работать» |

### Что убрать из README

- **Таблицы «Компонент / Alias / Назначение».** Технические имена пользователю не нужны. Назначение навыков переходит в блок «Что умеет агент», а внутренние навыки не упоминаются.
- **Описание внутренней механики:** температура модели, названия инструментов платформы, пути к файлам сборки.
- **Упоминания тестовых и демонстрационных данных.** README описывает работу на настоящих данных пользователя.
- **Общие фразы без содержания** («результат зависит от качества данных»), если они не говорят, что будет в конкретном случае.

### Правила написания

1. **Функции — словами пользователя:** «Проверка договора», а не `review-contract`.
2. **У каждой функции — конкретный результат:** что за документ, в каком формате, какие в нём поля.
3. **У каждого набора данных — последствие отсутствия:** агент остановится, спросит, сделает часть или ответит только по другим источникам.
4. **Только то, что работает сейчас.** Планируемые подключения в список возможностей не входят.
5. **Простые слова вместо терминов:** «база знаний пространства» вместо RAG, «подключённая система» вместо MCP, «файлы пространства» вместо workspace.
6. **Команды — только русскими названиями,** как в поле `name` файла из `commands/`. Если команд несколько — столбец в таблице функций. Если одна — упоминание в блоке «Как работать».

## 2. Откуда брать содержание

README не нужно писать с нуля: почти всё уже есть в файлах сборки.

| Блок README | Источник в сборке |
|---|---|
| Название, описание | `plugin.yaml`, шапка файла в `agents/` |
| Что умеет агент | Таблица навыков в файле агента; в `SKILL.md` — разделы «Операция», «Когда запускать», «Результат» |
| Какие данные нужны | `SKILL.md` — раздел «Вход» и правила раздела «Проверка»: что агент делает без данных |
| Как работать, команды | `commands/`, принципы в файле агента |
| Границы работы | Файл агента — раздел «Границы» |

Раздел «Вход» есть только в 72 из 143 `SKILL.md`. Для остальных навыков входные данные придётся извлекать из текста методики.

## 3. Шаблон для копирования

Текст в угловых скобках заменить, необязательные блоки удалить, если условие не выполнено.

```markdown
# <Название роли>

<Для кого агент и какую работу ведёт.> <С какого шага и до какого результата.>
<Чем особенно полезен или на что опирается, если это важно.>

## Что умеет агент

| Функция | Когда использовать | Что вы получите |
|---|---|---|

## Какие данные нужны

Агент работает с: <файлами из чата / документами пространства / базой знаний / подключёнными системами / сайтами>.

| Функция | Нужно обязательно | Желательно | Если данных нет |
|---|---|---|---|
| <Название функции> | <Файлы и сведения> | <Что улучшит результат> | <Спросит / сделает часть / укажет пробел / остановится> |

<!-- Необязательный блок: только если часть функций зависит от внешней системы -->
## Подключения

| Функция | Система | Без подключения |
|---|---|---|
| <Название функции> | <Система> | <Что работает на файлах> |

<!-- Необязательный блок: только если без настройки агент не работает -->
## Подготовка перед запуском

1. <Что загрузить в базу знаний>
2. <Какие параметры компании заполнить>

## Как работать

1. **Опишите задачу** обычными словами или запустите команду <название>. Укажите <что важно: объект, период, контрагента>.

- «<Запрос к функции 2>»
```

## 4. Пример заполнения — «Юрист по договорам»

Собрано из файлов сборки `contract-claims-agent`. Деление на «нужно» и «желательно» предложено при подготовке примера, в навыках его нет: перед применением его должен подтвердить автор агента.

---

> # Юрист по договорам
>
> Помогает юристу вести договорную работу: проверяет условия и полномочия подписанта, готовит протокол разногласий и оценивает договорные претензии. Результат — материалы для решения юриста с точными ссылками на пункты договора и документы.
>
> ## Что умеет агент
>
> | Функция | Когда использовать | Что вы получите |
> |---|---|---|
> | Проверка договора | Договор нужно проверить перед согласованием или понять, как изменились условия | Карта рисков и таблица отклонений: пункт, эталон или основание, отличие, последствие, предлагаемая позиция, вопрос |
> | Подготовка протокола разногласий | Есть карта рисков или согласованные замечания | Проект протокола: пункт, было, предлагается, обоснование, требуемое согласование; список нерешённых вопросов |
> | Оценка договорной претензии | Есть нарушение или претензия и нужна доказательная позиция | Хронология, матрица доказательств, воспроизводимый расчёт неустойки, проект позиции |
>
> ## Какие данные нужны
>
> Агент работает с файлами, которые вы загружаете в чат или кладёте в пространство. Внешние системы не подключаются и не изменяются.
>
> | Функция | Нужно обязательно | Желательно | Если данных нет |
> |---|---|---|---|
> | Проверка договора | Договор и приложения | Шаблон с редакцией, КП или спецификация, чек-лист компании, основания полномочий, правовые источники | Без шаблона агент не заявляет соответствие стандарту компании; без правового источника не объявляет условие незаконным |
> | Подготовка протокола разногласий | Точная редакция договора, проверенные замечания | Переговорная позиция, разрешённый шаблон протокола | Выполняет возможную часть и указывает пробелы |
> | Оценка договорной претензии | Договор, обязательство и срок, документы исполнения и уведомлений | Платежи, хронология, условия санкции и предел расчёта | Считает только подтверждённые базу, период и ставку; пробелы указывает |
>
> ## Как работать
>
> 1. **Опишите задачу** обычными словами или запустите команду «Запуск работы — Юрист по договорам».
> 2. **Приложите документы** в чат или положите их в пространство.
> 3. **Получите результат:** сначала вывод, затем основания, охват проверки, ограничения и следующий шаг.
> 4. **Проверьте результат.** Все материалы — проекты для юриста.
>
> ## Рекомендуемые цепочки
>
> - От проверки к правкам: `Проверка договора → Подготовка протокола разногласий`.
>
> ## Примеры запросов
>
> - «Сравни проект договора с утверждённым шаблоном и условиями КП — покажи риски до подписания»
> - «Подготовь протокол разногласий по проверенным замечаниям в формате было — предлагается»
> - «Разбери договорную претензию и рассчитай неустойку по указанным условиям и подтверждённой хронологии»
>
> ## Границы работы
>
> **Агент не делает:** земельную проверку, судебные документы и процессуальные сроки, расчёт госпошлины, мониторинг законодательства, запись в СЭД.
>
> **Решает человек:** правовую позицию, подписание, направление претензии и обращение в суд утверждает юрист.

## 5. Как были устроены README до перехода на шаблон

### Пять форматов

| Формат | Кол-во | Набор разделов | Сильная сторона | Главный пробел |
|---|---|---|---|---|
| **Операции** | 15 | Операция → результат, Примеры, Что делает человек | Ясный результат каждой функции | Нет входных данных; одинаковый абзац о файлах во всех 15 |
| **Состав** | 14 | Таблица компонентов, Примеры; иногда Ограничения, Как работать | Коротко | Технические имена, почти нет данных и границ |
| **Полный** | 3 | Функциональность, Как работать, Входные данные, Результаты, Примеры, Ограничения | Полнота | Результаты описаны общим абзацем, а не по функциям |
| **Инструкция** | 2 | Что умеет, Команды, Как начать, Данные, Работа с данными, Цепочки | Лучшее описание данных и команд | Объём до 120 строк, нет примеров запросов |
| **Особые** | 2 | Агроном и Фабрика агентов: свой набор разделов | Агроном — лучший пример на языке пользователя | Не повторяются |

Объём — от 16 до 123 строк, то есть различие почти в восемь раз.

### Покрытие блоков

| Блок | Есть в README из 36 | Комментарий |
|---|---|---|
| Описание агента | 36 | В 15 README — одно предложение |
| Перечень функций | 36 | В 14 — таблица компонентов |
| Результат по каждой функции | 18 | |
| Отдельный блок о входных данных | 7 | Разбивка по функциям — только в 5 |
| Как работать | 8 | |
| Примеры запросов | 33 | Нет у Фабрики агентов, ТОиР, ОТПиБ |
| Границы, ограничения | 23 | |

Самый большой разрыв — входные данные: в 29 из 36 README нет отдельного блока о том, что нужно агенту для работы.

### Что взято в шаблон

- Таблица «функция → результат» — из формата «Операции».
- Данные по функциям — из форматов «Полный» и «Инструкция» (ТОиР, Закупщик аптечной сети).
- Последствие отсутствия данных и простой язык — из README Агронома.
- Блок о решениях человека — из «Операций» и ОТПиБ.
- Цепочки и работа с данными — из ТОиР и ОТПиБ, как необязательные блоки.
