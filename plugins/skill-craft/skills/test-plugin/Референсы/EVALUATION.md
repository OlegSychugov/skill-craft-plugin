# Evals: кейсы, прогон, вердикт

Автоматического раннера нет: прогон делается вручную на демо-стенде
Cowork, а грейдинг — в среде разработчика по уликам, то есть по
факт-отчёту агента и скачанным артефактам сессии.

`evals/` создаётся только по просьбе пользователя (вызов `test-plugin`).
Если в плагине есть `evals/`, публикация требует вердикта PASS последнего
прогона. Если `evals/` нет — гейта нет.

## 1. Структура

```
<cfg:testing_dir>/<alias>/
  Данные агента <Название>/      fixtures — кейсы ссылаются на них по имени, не копируют
  evals/
    кейс-<имя>/prompt.md         живая фраза без имени навыка + canned-ответы на question
    кейс-<имя>/graders.md        проверки PASS/FAIL, фиксируются до прогона
    ПРОТОКОЛ_DEMO.md             пошаговый прогон на стенде
    get-evals-result.md          промпт-сборщик факт-отчёта под этот плагин
    results/<ГГГГ-ММ-ДД>/        факты.md + артефакты/ + вердикт.md
```

## 2. Кейсы

Минимум три кейса:

| Источник в SKILL.md / плане | Кейс | Ожидание |
|---|---|---|
| триггеры | позитивный | навык срабатывает, артефакты созданы |
| анти-триггеры («Не сюда») | негативный | навык не активируется |
| пограничные случаи | edge | поведение по заявленной стратегии |

Промпт формулируется так, как пользователь говорит вживую: «сделай мой
еженедельный отчёт для начальника», а не «запусти навык weekly-report».
Canned-ответы на `question` нужны, чтобы повторные прогоны можно было
сравнивать.

## 3. Градеры

- **Артефактные (первичные)** — содержимое скачанных файлов: структура
  (листы xlsx, блоки HTML), числа против ожиданий fixtures, имена файлов,
  запись только в `/session`.
- **Инструментальные** — последовательность вызовов по факт-отчёту:
  документы создаются через профильные тулы, а не `python_run`; `todo`
  появляется до первого ответа; не больше заявленного числа раундов
  `question`; нет служебных файлов.
- **Рубрика** — «PASS если … / FAIL если …» по критериям качества плана.
  Критические ошибки плана — обязательные градеры: FAIL любого из них
  означает FAIL всего кейса.

## 4. ПРОТОКОЛ_DEMO.md

1. Плагин установлен на стенде (`deploy-plugin`).
2. Новая сессия, загружены fixtures.
3. Кейсы по порядку; на `question` отвечать canned-ответом.
4. На приёмке — 2 прогона на кейс, каждый в свежей сессии; на итерациях
   доработки — 1 прогон.
5. После прогонов вставить `get-evals-result.md`, скопировать
   факт-отчёт целиком.
6. Скачать артефакты сессии.
7. Сложить всё в `evals/results/<дата>/` → `test-plugin <alias> grade <дата>`.

## 5. get-evals-result.md

Промпт для сессии стенда. Агент стенда по нему собирает отчёт по
шаблону `факты.md`: файлы сессии с путями, вызовы тулов по каждому кейсу,
заданные вопросы и ответы, аномалии. Имена кейсов и ожидаемые
артефакты вшиваются в промпт. Он не заменяет скачивания артефактов.

## 6. факты.md

Только факты, без оценок: «вызвал `python_run` для xlsx» — да, «вроде
нормально» — нет.

```
# Факты прогона <дата>, стенд <название>

## Кейс <имя>, прогон 1
- Промпт: <текст>
- Вызовы тулов по порядку: <тул, аргументы, результат>
- Вопросы агента / ответы: <…>
- Созданные файлы: <имя, путь, размер>
- Аномалии: <ошибки, повторы, отклонения; «нет»>
```

## 7. вердикт.md

```
# Вердикт по <alias>, <дата>

| Кейс | Прогоны | Статус | Главное замечание |
|---|---|---|---|
| кейс-<имя> | 2/2 PASS | PASS | … |

Итог: PASS / FAIL
```

PASS ставится, если все кейсы пройдены в обоих прогонах и не упал ни
один критический градер. Каждый FAIL привязан к градеру и улике: файл
и место (строка артефакта, вызов из факты.md, блок ответа).

## 8. Недетерминизм

- Если два прогона разошлись, разбирать улики обоих, а не усреднять.
- Нестабильное срабатывание навыка на живой фразе — это находка (обычно
  про description), а не повод перезапускать до удачи.
- **Δ-плечо** (необязательно, при первой приёмке и после правки
  description): те же промпты с отключённым навыком. Если ответ
  сопоставим — навык не добавляет ценности; пересматривать надо его
  пользу, а не кейсы.
