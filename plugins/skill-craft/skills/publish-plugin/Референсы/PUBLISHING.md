# Публикация в витрину (gitverse)

Репозиторий: `<cfg:hub_repo_url>`. Все изменения идут только через PR
после ревью; в `<cfg:hub_base_branch>` напрямую не пушат.

## Регламент веток

gitverse вливает PR squash-коммитом, поэтому git навсегда считает ветку
«не слитой», и без дисциплины ветки копятся. Отсюда правила:

- **Создание** — только от свежей базовой ветки (pull перед созданием),
  никаких веток от веток.
- **Имя** — `feature/<alias>` (латиница, кебаб). Одна задача — одна
  ветка — один MR. Пакет плагинов одной линейки — одна ветка
  `feature/<линейка>-package`, и это осознанное решение.
- **Пуш** — `git push -u origin feature/<alias>`: upstream сразу
  правильный, никогда не базовая ветка.
- **После принятия MR, в тот же день** — удалить ветку на gitverse,
  `fetch --prune`, локально `branch -D` (после squash `-d` не сработает,
  это нормально).
- **Ветка живёт недели, не месяцы.** Если базовая ветка ушла вперёд,
  сначала влить её в свою.

## Шаблон описания PR

- **Название** — что добавлено.
- **Описание** — кратко, что делает плагин.
- **Категория** — одна из 7 (`METHODOLOGY.md` §3).
- **Задача** — какую задачу пользователя решает.
- **Как тестировать** — сценарий проверки на тест-данных.
- **Чек-лист** — самопроверка по чек-листу приёмки skill-craft.

## Что проверяет тестировщик

На ветке PR автоматически поднимается тестовый стенд. Тестировщик
проверяет:
- структуру: путь, alias, YAML-заголовок, категорию, целый `version`,
  непустые `tags`;
- содержимое: название, описание, инструкцию, **тон и орфографию**;
- функциональность: плагин в витрине и в сессии.

Замечания приходят комментарием «Результаты тестирования», срок на
исправления — 2–3 рабочих дня.

## Доступ

Push отвергнут с 403 — значит, нет прав. Доступ выдаёт администратор
репозитория витрины.
