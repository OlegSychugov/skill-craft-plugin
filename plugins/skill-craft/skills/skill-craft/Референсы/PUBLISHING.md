# Публикация навыков и плагинов в репозиторий

> **Источник:** инструкция по публикации в репозиторий витрины, прислана
> пользователем 2026-08-20. Сохранена дословно (утраченные при передаче
> таблицы восстановлены как Markdown-таблицы). Файл лежит в `.kilo/`
> (Референсы навыка `skill-craft`), исключён из git целиком и никогда
> не пушится в gitverse.

Репозиторий: <cfg:hub_repo_url>

Этот репозиторий используется для витрины навыков и плагинов. Доступ к нему
выдаёт администратор репозитория — запросите его у ответственного за витрину.

## ⚠️ Важное правило

Никогда не пушите напрямую в ветку master!

Все изменения вносятся только через пул-реквест (PR) после ревью.

## 📋 Пошаговая инструкция

### Шаг 1. Обновите локальную версию репозитория

Перед началом работы убедитесь, что у вас актуальная версия master:

```bash
git checkout master
git pull origin master
```

### Шаг 2. Создайте новую ветку

Название ветки зависит от типа изменений:

| Тип изменения | Ветка | Пример |
|---------------|-------|--------|
| Новый навык | `skill-<slug>` | `skill-pdf-converter` |
| Новый плагин | `plugin-<slug>` | `plugin-telegram-bot` |

**Что такое `<slug>`?**

Это короткое название на английском в нижнем регистре, слова разделяются
дефисом. Без пробелов и специальных символов.

```bash
# Для навыка
git checkout -b skill-<slug>

# Для плагина
git checkout -b plugin-<slug>
```

Пример:

```bash
git checkout -b skill-pdf-converter
```

### Шаг 3. Внесите изменения

Добавьте файлы навыка или плагина в репозиторий:

```bash
# Добавьте новые или изменённые файлы
git add <имя_файла>

# Или добавьте все изменения
git add .
```

### Шаг 4. Сделайте коммит

Напишите понятное сообщение коммита на русском или английском:

```bash
git commit -m "Добавлен навык: <название>"
# или
git commit -m "Добавлен плагин: <название>"
```

Пример:

```bash
git commit -m "Добавлен навык: Конвертация PDF в текст"
```

### Шаг 5. Отправьте ветку на сервер

```bash
git push origin <название-ветки>
```

Пример:

```bash
git push origin skill-pdf-converter
```

### Шаг 6. Создайте пул-реквест

1. Откройте репозиторий в браузере: <cfg:hub_repo_url>
2. Перейдите на вкладку Pull Requests (или Merge Requests)
3. Нажмите New Pull Request (или Create Merge Request)
4. Выберите:
   - Base branch: `master`
   - Compare branch: ваша ветка (например, `skill-pdf-converter`)
5. Заполните описание:
   - Название: что добавлено
   - Описание: кратко, что делает навык/плагин
6. Нажмите Create Pull Request

### Шаг 7. Ожидайте ревью

После создания PR:

- Команда проведёт код-ревью
- При необходимости запросит правки
- После одобрения PR будет влит в master

**Не удаляйте ветку до завершения ревью!**

## 🔧 Если потребовались правки после ревью

1. Внесите изменения в файлы
2. Сделайте коммит:

```bash
git add .
git commit -m "Исправлены замечания ревью"
```

3. Отправьте изменения:

```bash
git push origin <название-ветки>
```

Коммиты автоматически добавятся в существующий пул-реквест.

## ❗ Частые ошибки и как их избежать

| Ошибка | Как исправить |
|--------|---------------|
| Забыли создать ветку и работаете в master | Отмените изменения: `git reset --hard HEAD~1`, затем создайте ветку |
| Запушили в master напрямую | Срочно сообщите команде — ветку нужно будет откатить |
| Конфликт слияния при создании PR | Обновите ветку: `git pull origin master`, разрешите конфликты, запушьте снова |
| Непонятное сообщение коммита | Переименуйте: `git commit --amend -m "Новое сообщение"` + `git push --force` |

## 📞 Если что-то пошло не так

Обратитесь к команде разработки или оставьте комментарий в пул-реквесте
с описанием проблемы.

## 📌 Краткая шпаргалка

```bash
# 1. Обновить master
git checkout master
git pull origin master

# 2. Создать ветку
git checkout -b skill-<slug>

# 3. Добавить файлы
git add .

# 4. Закоммитить
git commit -m "Добавлен навык/плагин: <название>"

# 5. Отправить ветку
git push origin skill-<slug>

# 6. Создать PR через веб-интерфейс
```

## Локальное дополнение 2026-09-11: актуальный процесс («Обзор процесса»)

> **Источник:** инструкция «Обзор процесса» работы с витриной cowork_hub,
> прислана пользователем 2026-09-11. Дословный текст 2026-08-20 выше
> сохранён для истории; при расхождениях приоритет у этого дополнения.

Дельты к дословной инструкции выше:

1. **Ветки:** `feature/<alias>` — единый шаблон вместо
   `skill-<slug>`/`plugin-<slug>` (старые шаблоны устарели).
2. **Целевая ветка PR:** master (или main — по инструкции).
3. **Commit:** `feat: добавить навык <Название>` (вместо
   «Добавлен навык: …»).
4. **Шаблон описания PR** — полный, шесть секций:
   - **Название** — что добавлено;
   - **Описание** — кратко, что делает навык/плагин;
   - **Категория** — alias из `categories.yaml`;
   - **Задача** — какую задачу пользователя решает;
   - **Как тестировать** — сценарий проверки;
   - **Чек-лист** — самопроверка перед сдачей.
5. **Ревьюеры:** назначаются из команды GigaCowork.
6. **Этап тестирования:** на ветке PR автоматически поднимается тестовый
   стенд (GitVerse CI, статус Deployed). Чек-лист тестировщика:
   - структура и форматирование: путь и alias, YAML-заголовок, категория,
     `version` — целое число, `tags` — непустой список;
   - содержимое: название, описание, инструкция, тон, орфография;
   - функциональное тестирование: в витрине и в сессии.
   Результат оформляется комментарием по шаблону «Результаты
   тестирования»; срок исправлений — 2–3 рабочих дня; после Request
   Changes — повторное тестирование.
7. **После merge:** CI/CD валидирует структуру и YAML, обновляет индекс,
   деплоит; синхронизация 2–5 минут. Проверка публикации: поиск по
   названию/категории/тегам, версия, карточка.
8. **Жизненный цикл дальше:** одобрение администратором компании
   (локальная версия объекта, каталог компании) → установка пользователем
   в пространства: один навык — одна установка на пространство;
   отключение — независимо по пространствам; обновление — централизованно
   после одобрения администратором.
9. **Ограничения MVP:** нет создания/редактирования витрины через Cowork
   UI; нет системных навыков для всех; нет выбора исторической версии;
   нет автообновления; нет отката; нет разных версий одного навыка в
   разных пространствах.

## Локальное дополнение 2026-09-28: карта плагинов

Публикация не завершается мержем: статус сущности отражается в карте
графа `<cfg:plugins_map_path>`
(формат и процедура — `Референсы/PLUGINS-MAP.md`):

- после пуша ветки (шаг 5) — `STATUS="remote-branch"` у узла плагина;
- после merge PR (шаг 7) — `STATUS="published"`, обновить `VERSION` и
  `UPDATED`; если плагина ещё не было в карте — узел добавляется сразу;
- ревизия сущности при правках после ревью — актуализировать
  `annotation`, `keywords`, связи.
