# Тестирование поведения навыков: evals, прогон, вердикт

> **Условие активации (opt-in):** eval-слой применяется только по явной
> просьбе пользователя («прогони evals», «собери evals», «проверь
> поведение навыка на демо-стенде»). Без просьбы — не создавать
> `evals/`, не прогонять кейсы, не требовать вердикт, не блокировать
> публикацию.

## 1. Суть и место в процессе

Навык может быть структурно безупречен (чек-лист приёмки пройден) и
содержательно аккуратен (ревью пройдено), но не срабатывать на живой
фразе пользователя или нарушать запреты при исполнении. Это слой
поведения, и его закрывают evals.

Три слоя контроля качества:

| Слой | Инструмент | Статус |
|---|---|---|
| Структура | чек-лист приёмки skill-craft | есть |
| Содержание | ручное ревью тела | есть |
| Поведение | evals (этот документ) | по запросу пользователя (opt-in) |

Автоматического раннера нет, поэтому:

- **прогон** — вручную на демо-стенде Cowork по `ПРОТОКОЛ_DEMO.md`;
- **грейдинг** — в среде разработчика по возвращённым уликам:
  факт-отчёт агента + скачанные артефакты сессии;
- **вердикт** — гейт перед публикацией: `/опубликуй-плагин` требует
  `evals/results/<дата>/вердикт.md` со всеми кейсами PASS; гейт
  действует, только когда eval-слой активирован явной просьбой
  пользователя, иначе публикация вердикта не требует.

Eval-слой — не часть контракта витрины: `METHODOLOGY.md` не меняется.

## 2. Структура evals/

`evals/` живёт в Testing-папке плагина, рядом с fixtures:

```
<cfg:testing_dir>/<alias>/
  …плагин по стандарту skill-craft (plugin.yaml, skills/, README.md)…
  Данные агента <Название>/     # fixtures — синтетика (шаг 8 /сделай-плагин)
  evals/
    кейс-<имя>/prompt.md        # естественная фраза (БЕЗ имени навыка) + canned-ответы на question
    кейс-<имя>/graderы.md       # PASS/FAIL-рубрики + детерминированные проверки
    ПРОТОКОЛ_DEMO.md            # пошаговый прогон на демо-стенде
    get-evals-result.md         # промпт-сборщик факт-отчёта (генерируется под плагин)
    results/<дата>/             # факты.md + артефакты/ + вердикт.md (после прогона)
```

Fixtures не копируются в `evals/` — кейсы ссылаются на файлы из
«Данные агента …» по имени. Прогоны и результаты — только в
`evals/results/<дата>/`, дата в формате `ГГГГ-ММ-ДД`.

## 3. Источники кейсов

Кейсы выводятся из SKILL.md / ТЗ черновика, не выдумываются:

| Раздел ТЗ | Тип кейса | Ожидание |
|---|---|---|
| «Триггеры активации» | позитивный | навык срабатывает, артефакты созданы |
| Анти-триггеры (когда НЕ использовать) | негативный | навык НЕ активируется, обычный ответ агента |
| «Пограничные случаи» | edge-кейс | поведение по заявленной в ТЗ стратегии |

Минимальный набор — 3 кейса: триггер, анти-триггер, пограничный.

Промпты — естественные формулировки, как пользователь говорит вживую:
без имени навыка и служебных слов («сделай мой еженедельный отчёт для
начальника» — да; «запусти навык weekly-report» — нет). Если в черновике
нет анти-триггеров или пограничных случаев — помечать `<TBD>` и вопрос в
сводку, не выдумывать.

В каждом `prompt.md` фиксируются canned-ответы на возможный `question`
агента — чтобы повторы прогона были сравнимы.

## 4. Типы graderов

Грейдинг — в среде разработчика по уликам прогона. Три типа грейдеров;
при расхождении первичны артефакт-детерминированные (отчёт агента может
галлюцинировать, файлы — нет).

### Артефакт-детерминированный

Проверка содержимого файлов, скачанных из сессии:

- структура HTML-артефакта кодом (BeautifulSoup: обязательные блоки,
  строки таблиц, сбалансированность тегов, inline CSS, `lang`,
  `charset`);
- числа в артефактах против ожиданий fixtures: детерминированные входы
  дают детерминированные выходы (образец — сценарии treasury-assistant:
  фиксированные входы, ожидания вида «итог = 399 500 RUB, разрыв
  10 октября, найдены все 8 посаженных проблем»);
- состав листов .xlsx, имена созданных файлов, запись только в `/session`.

### Инструментальный

Проверка последовательности вызовов по факт-отчёту:

- создание документов — системные навыки `sys-*` (`word`, `excel`), не
  `python_run`;
- `todo` сформирован до первого текстового ответа;
- `question` — не более заявленного числа раундов (обычно 1);
- записи только в `/session`, не в workspace.

### Рубрика (llm-судья)

- Оценка ответа по рубрике «PASS если … / FAIL если …», выведенной из
  «Критериев качества» ТЗ. Рубрика фиксируется в `graderы.md` до
  прогона.
- «Критические ошибки» ТЗ — обязательные graderы: FAIL любого из них =
  FAIL кейса независимо от остальных проверок.

## 5. Шаблон ПРОТОКОЛ_DEMO.md

Пошаговая инструкция прогона на демо-стенде:

1. Установить плагин из Testing-папки на демо-стенде.
2. Создать сессию, загрузить fixtures из «Данные агента …».
3. Пройти кейсы по порядку; промпт — из `prompt.md`. Если агент задаёт
   `question` — отвечать canned-ответом из `prompt.md` (фиксированы для
   повторяемости прогонов).
4. На приёмке — 2 прогона на кейс (каждый прогон — свежая сессия);
   на итерациях доработки — 1 прогон.
5. После всех прогонов вставить промпт из `get-evals-result.md` в
   сессию, получить факт-отчёт, скопировать его целиком.
6. Скачать артефакты сессии (файлы из `/session`).
7. Собрать `evals/results/<дата>/`: `факты.md`, `артефакты/`; проградировать
   грейдерами из `кейс-*/graders.md` и записать `вердикт.md`.

Δ-плечо (раздел 10) — опциональной серией после основного прогона.

## 6. Промпт-сборщик get-evals-result.md

Промпт, который вставляется в сессию демо-стенда ПОСЛЕ прогонов. Агент
стенда собирает факт-отчёт по шаблону `факты.md`, готовый к
копированию:

- список файлов сессии (загруженные и созданные, с путями);
- последовательность вызовов тулов по каждому кейсу;
- заданные агентом вопросы и данные на них ответы;
- аномалии: ошибки тулов, повторы вызовов, отклонения от ожиданий.

Требования:

- генерируется `/сделай-плагин` под конкретный плагин — вшиты имена
  кейсов и ожидаемые артефакты;
- НЕ заменяет ручное скачивание артефактов;
- факт-отчёт — улика поведения, артефакты — улика результата; при
  расхождении первичны артефакт-graderы.

## 7. Шаблон факты.md

Правило: факты, не выводы. «Вызвал `python_run` для xlsx» — да;
«вроде нормально» — нет.

```
# Факты прогона <дата>, стенд <название>

## Кейс <имя>, прогон 1
- Промпт: <текст>
- Вызовы тулов по порядку: <тул, аргументы, результат>
- Вопросы агенту / ответы: <текст вопросов и canned-ответов>
- Созданные файлы: <имя, путь, размер>
- Аномалии: <ошибки, повторы, отклонения; «нет» — если не было>

## Кейс <имя>, прогон 2
…

## Δ-плечо (если выполнялось)
…
```

## 8. Формат вердикт.md

```
# Вердикт по <alias>, <дата>

| Кейс | Прогоны | Статус | Главное замечание |
|---|---|---|---|
| кейс-<имя> | 2/2 PASS | PASS | … |

Итог: PASS / FAIL
```

- Порог PASS: все кейсы пройдены и ни один критический grader не упал.
- Каждый FAIL привязан к grader и улике: файл + место (строка
  артефакта, вызов тулa из факты.md, блок ответа).
- Вердикт пишется в `evals/results/<дата>/вердикт.md` и служит входом
  для `/опубликуй-плагин`; вход требуется только при активированном
  eval-слое — по явной просьбе пользователя (см. «Условие активации»
  в начале документа), иначе публикация вердикта не требует.

## 9. Правила недетерминизма

- На приёмке — 2 прогона на кейс: оба проходные → PASS; расхождение →
  разбирать по уликам обоих прогонов, не усреднять.
- Одиночный прогон допустим только на итерациях доработки, не на
  приёмке.
- Нестабильное срабатывание навыка на естественной фразе — находка
  (обычно про description), а не шум для повтора до удачи.

## 10. Δ-плечо (прогон без навыка)

Опционально: одна серия на навык при первой приёмке; повторно — после
правок `description`. Навык отключён, промпты те же, что в основном
прогоне.

Интерпретация:

- стенд без навыка отвечает сопоставимо → навык не добавляет ценности,
  пересматривать пользу, а не чинить кейсы;
- «навык не сработал на естественную фразу» в основном прогоне →
  править `description`, не кейс: кейс отражает живую формулировку
  пользователя.

## 11. Запреты на перенос и публикацию

- `evals/` и `results/` — внутренние QA-материалы: никогда не
  переносятся в `plugins/` и не пушатся в витрину gitverse.
- При публикации `evals/` сохраняется на месте в Testing-папке как
  история прогонов; остальное содержимое Testing-папки удаляется по
  команде публикации.
- Существующие плагины в Testing без `evals/` — валидная ситуация
  (аналог «тестовые данные не обнаружены»); evals досоздаются при
  следующей доработке плагина.
