# Методология переработки skills и plugins

> **Источник:** методология контракта витрины, прислана пользователем
> 2026-08-19, повторно подтверждена 2026-08-21 (текст без изменений). Сохранена дословно (таблицы полей приведены к Markdown-таблицам).
> Файл лежит в `.kilo/` (Референсы навыка `skill-craft`), исключён из git
> целиком и никогда не пушится в gitverse.

## 1. Общее

Контент витрины хранится в git-репозитории. Корень репозитория:

- `categories.yaml` - общий справочник категорий
- `skills/` - папка навыков
- `plugins/` - папка плагинов

Каждая сущность (навык или плагин) - отдельная папка внутри skills/ или
plugins/; имя папки = ее идентификатор (alias).

**Правила для alias:** только латинские буквы, цифры, дефис и подчёркивание;
до 64 символов; уникален в пределах своего типа.

## 2. Категории (categories.yaml)

| Поле | Обяз. | Описание |
|------|-------|----------|
| `alias` | да | идентификатор категории, тот же формат, что и alias сущности |
| `name` | да | отображаемое название |
| `type` | нет | к какому типу сущностей относится категория (если не указан - общая). Возможные значения: `skill`, `plugin` |
| `order` | нет | порядок сортировки |

Категория, указанная у навыка или плагина, обязана существовать в этом
справочнике - иначе сущность не пройдет проверку при синхронизации.

## 3. Навык - контракт (skills/&lt;alias&gt;/SKILL.md)

Один файл SKILL.md с YAML-заголовком в начале:

| Поле | Обяз. | Описание |
|------|-------|----------|
| `name` | да | отображаемое имя навыка |
| `description` | да | краткое описание |
| `category` | да | alias категории из справочника |
| `version` | нет | номер версии, по умолчанию 1 |
| `tags` | нет | список тегов |

Все остальное содержимое файла (после заголовка) - тело навыка, инструкции
для агента. Дополнительные файлы/ресурсы кладутся в ту же папку.

### Пример навыка

`skills/tender-discount-calc/SKILL.md`:

```markdown
---
name: Расчет скидки для тендера
description: Считает итоговую скидку по объему заказа и сегменту клиента
category: sales
tags: [продажи, кп]
---

Ты помогаешь менеджеру по продажам рассчитать скидку для клиента.
Правила расчета:
1. Базовая скидка зависит от объема заказа...
2. ...
```

Плюс любые дополнительные файлы рядом в той же папке (например,
`reference.md` с таблицей ставок).

## 4. Плагин - контракт (plugins/&lt;alias&gt;/)

Обязательный файл `plugin.yaml` в корне папки плагина:

| Поле | Обяз. | Описание |
|------|-------|----------|
| `name` | да | отображаемое имя плагина |
| `description` | да | краткое описание |
| `category` | да | alias категории из справочника |
| `version` | нет | номер версии, по умолчанию 1 |
| `tags` | нет | список тегов |
| `ui` | нет | собственный визуальный элемент плагина, если есть |

Состав плагина - вложенные папки:

- `skills/<alias>/SKILL.md` - навыки в составе плагина (те же поля, что в
  п. 3, но без собственной категории - категория есть только у плагина
  целиком)
- `commands/<alias>.md` - команды плагина, обязательны name/description в
  заголовке
- `agents/<alias>.md` - агенты плагина; поле skills в заголовке агента может
  ссылаться только на навыки этого же плагина - ссылка на чужой или внешний
  навык не пройдет проверку

**Ограничения:**

- Плагин не может быть пустым - нужен хотя бы один навык, команда или агент
- На каждый тип компонента - не более 20 штук в одном плагине
- Собственный визуальный элемент - опционален, не обязателен

### Пример плагина

Структура папки:

```
plugins/crm-lead-sync/
  plugin.yaml
  README.md
  skills/
    lead-scoring/
      SKILL.md
  commands/
    sync-leads.md
  agents/
    lead-manager.md
```

`plugin.yaml`:

```yaml
name: Синхронизация лидов CRM
description: Синхронизирует и скорит лидов между CRM и Cowork
category: sales
version: 2
tags: [crm, лиды]
```

`skills/lead-scoring/SKILL.md` - навык внутри плагина, без поля `category`,
категория есть только у плагина целиком:

```markdown
---
name: Скоринг лида
description: Оценивает лида по заданным критериям и присваивает приоритет
---

Инструкция по скорингу лида...
```

`commands/sync-leads.md`:

```markdown
---
name: Синхронизировать лидов
description: Запускает синхронизацию лидов из CRM в текущее пространство
---

Сделай ${что}.
```

`agents/lead-manager.md` - skills может ссылаться только на навыки этого же
плагина (здесь - `lead-scoring`), model/temperature необязательны:

```markdown
---
name: Менеджер по лидам
description: Приоритизирует и обрабатывает лидов
skills: [lead-scoring]
temperature: 0.3
---

Ты - агент, отвечающий за приоритизацию лидов.
```

### Пример со своим UI-элементом

Добавка в `plugin.yaml`, если у плагина есть визуальный элемент:

```yaml
name: Виджеты
description: Плагин со своим экраном
category: dev
ui:
  entry: ui/dist/index.js
```

Файл `ui/dist/index.js` должен физически лежать в папке плагина по
указанному пути - иначе плагин целиком не пройдет синхронизацию.

## Стандарт качества чистовика

Краткая выжимка; детали и образцы — в `SKILL-AUTHORING.md`
(Референсы навыка `skill-craft`).

1. `name` — отглагольное существительное (действие-результат).
2. `description` = что делает + контекст применения (для кого, для каких задач) — без дословных триггерных и анти-триггерных фраз; триггеры, анти-триггеры и неформальные сигналы — в разделе тела «Когда использовать (триггеры)».
3. Степень свободы агента указана явно (высокая/средняя/низкая).
4. Тело SKILL.md — до 500 строк; излишки выносятся в `Референсы/`.
5. Ссылки на ресурсы — один уровень глубины (SKILL.md → файл `Референсы/`).
6. Длинные справочники (100+ строк) — с оглавлением в начале.
7. Многошаговые процессы — с копируемым чек-листом прогресса.

## Локальное дополнение: валидный YAML-заголовок (frontmatter)

> **Источник:** рабочее правило после ошибок импорта 2026-09-10
> (plain-`description` с «: » падал на разборе) + замечание валидатора
> 2026-09-11: символ `|-` попадает в описание витрины — Hub не
> разбирает блочные скаляры. Канон `|-` отменён. Не часть присланного
> контракта.

Касается всех YAML-заголовков: `SKILL.md`, `plugin.yaml`,
`commands/*.md`, `agents/*.md`.

- `description` — **одна plain-строка**: без блоков `|-`/`>`, без
  кавычек и без «: » (двоеточие+пробел) в тексте; перечисления — через
  «—», не «: ». Принятый образец в каталоге:
  `plugins/document-manager/plugin.yaml`.
- `name` — одна строка без «: ».
- `tags` — slug-теги: строчные, без пробелов; многословные — через дефис
  (`база-знаний`). Единообразны в `plugin.yaml` и SKILL.md навыков
  плагина.
- Обязательность при публикации: все пять полей — `name`,
  `description`, `category`, `version`, `tags`; `version` — целое
  число; `tags` — непустой список.
- Закрывающий разделитель заголовка — один `---` (задвоенный `---` в
  примере присланной инструкции — артефакт копипаста, не канон).

Канонический образец:

```yaml
---
name: Составление нового ТЗ
description: Готовит ТЗ по ГОСТ 34.602-2020 для автоматизации ИТ-системы — от сбора требований до структуры документа
tags: [тз, гост-34-602]
---
```

Если перенос строки необходим — plain-продолжение (отступ 2 пробела),
но без «: » в тексте; предпочтителен один физический
абзац-строка. Примеры в дословных разделах 3–4 выше показывают
минимальный допустимый вид полей; при авторинге для каталога всегда
применяй plain-канон.

## Локальное дополнение: агент плагина обязателен

> **Источник:** указание пользователя 2026-10-05. Не часть присланного
> контракта: §4 допускает плагин из одних навыков или команд — рабочее
> правило каталога ужесточает его так же, как правило категорий.

- В каждом плагине — минимум один агент `agents/<alias>.md`; главный по
  умолчанию — `agents/<plugin-alias>.md`. Плагин без агента не проходит
  приёмку, развёртывание и публикацию.
- `skills` агента перечисляет все навыки плагина и только их — в обе
  стороны: нет ссылок на чужие навыки, нет навыков без агента.
- `name` агента — роль («Рекрутер»), а не отглагольное существительное:
  исключение из правила `name` навыков.
- Тело — разделы «Роль», «Навыки», «Принципы» (с маршрутизацией
  «ситуация → навык»), «Границы».

Полный стандарт, шаблон и образцы — `AGENT-MD.md`.

## Локальное дополнение: правило выбора категорий

> **Источник:** указание пользователя 2026-08-20, актуализировано
> 2026-09-10 после ошибки импорта с категорией `support`; дополнено
> 2026-09-11 по инструкции «Обзор процесса» (расхождения с ней
> зафиксированы ниже). Не часть присланного контракта — рабочее правило
> переработки.

- Фактическое поле идентификатора в `categories.yaml` репозитория —
  `slug:` (инструкция «Обзор процесса» описывает его как `alias:` —
  расхождение зафиксировано, следует фактическому файлу).
- Backend Cowork поддерживает **только семь категорий**; другие значения
  `category` не проходят импорт, даже если добавлены в `categories.yaml`:
  - `analytics` — Аналитика и финансы
  - `documents` — Документы и право
  - `management` — Менеджмент и HR
  - `sales` — Продажи и клиенты
  - `research` — Исследования и внедрение ИИ
  - `productivity` — Продуктивность
  - `development` — Разработка
- Пример категории `procurement` из инструкции недоступен — не входит
  в семь поддерживаемых.
- **Новые категории не создаются** — временное отклонение от инструкции
  «Обзор процесса» (она допускает PR с добавлением записей в
  `categories.yaml`): backend Cowork поддерживает только текущий
  справочник из семи категорий, одного изменения справочника Hub
  недостаточно. Новых записей в `categories.yaml` не создавать до
  отдельного расширения enum в приложении Cowork. Подбирай существующую
  категорию; узкие категории под конкретный плагин не создаются.
- Если категория используется и навыками, и плагинами, поле `type` у неё
  не указывается.
