## 1. Зачем: провалы проектирования без архитектурного слоя

На сложных проектах (дашборды, отчётные системы) проектирование
страдает одним и тем же дефектом: агент зарывается в детали в
отдельных местах и упускает очевидные архитектурные решения. Два
реальных кейса:

- агент устроил из референса навыка хранилище данных на excel —
  справочная папка навыка стала «базой данных» пользователя;
- агент не предложил вынести обработку данных в MCP-сервер и
  организовать нормальный ETL-процесс — вся обработка осталась в теле
  навыка.

Вывод: архитектурные решения о данных и интеграциях фиксируются до
декомпозиции и кода. Для этого методика добавляет отдельный этап —
«Архитектура данных и интеграций» — между выбором стека и детальным
проектированием.

## 2. Методика — пять этапов

Этапы по графу (Приложение А); этапы 3 и 4 графа перенумерованы в 4 и
5, между ними вставлен новый этап 3.

| Этап | Содержание | В графе |
|---|---|---|
| 1. Формулирование задачи и требований | уточнение требований с ИИ; анализ входных данных и форматов; границы MVP | этап 1 |
| 2. Выбор технологического стека и библиотек | список предпочтительных библиотек ИИ; критерии выбора инструментов; учёт версий Python и библиотек | этап 2 |
| 3. Архитектура данных и интеграций: ETL и MCP | ETL-решение; MCP-решение; дуальность режимов | **дополнение, не из графа** |
| 4. Проектирование и планирование реализации | архитектура приложения; декомпозиция на функции и модули; псевдокод/алгоритмы | этап 3 |
| 5. Генерация и аннотирование кода с ИИ | семантический шаблон разметки; инструкции для ИИ-агента по работе с кодом; стандарты логирования; контракты кода | этап 4 |

Почему этап 3 именно здесь: решения о данных и интеграциях принимаются
после требований и стека, но до декомпозиции — иначе декомпозиция
фиксирует случайную архитектуру, и режим «зарывания в детали»
повторяется.

Этапы 1, 2, 4, 5 ведутся по графу: узлы подпроцессов, ключевые слова
и аннотации в Приложении А — готовое содержание каждого этапа для
работы с пользователем. Ниже подробно раскрыт только новый этап 3.

## 3. Этап 3 подробно: архитектура данных и интеграций (ETL и MCP)

### ETL-решение

Рассмотреть необходимость ETL-механик, ответив вместе с пользователем:

| Вопрос | Что фиксировать |
|---|---|
| Источники данных | какие системы и файлы, кто владелец данных |
| Схемы и форматы | структура данных, форматы файлов, API-спецификации |
| Объёмы | размер, рост, пиковые нагрузки |
| Частота обновления | разовая загрузка / регулярная / real-time |

Альтернативы доставки данных — выбрать одну и зафиксировать:

1. **Файлы в сессии** — пользователь загружает файлы, обработка идёт
   в `/session`; достаточно для MVP и разовых отчётов.
2. **ETL-конвейер** — регулярная выгрузка-преобразование-загрузка вне
   навыка; нужен при регулярной отчётности и объёмах, неудобных для
   ручной загрузки.
3. **Прямая интеграция** — MCP-коннектор к системе-источнику (см.
   «MCP-решение» ниже).

Жёсткое правило: референсы навыка — не хранилище данных. Никаких
excel/json «баз данных» в `Референсы/` (кейс раздела 1). Референсы —
справочники, шаблоны, примеры; данные пользователя живут в его
ландшафте или загружаются в сессию.

### MCP-решение

Рассмотреть вынос доступа к данным и обработки в MCP-сервер. Критерии
«за»:

- интеграция переиспользуется несколькими навыками или агентами;
- объём и стабильность обработки не позволяют держать её в теле
  навыка;
- нужен real-time доступ к источникам (1С, CRM, почта);
- безопасность: доступ к внутренним системам оформляется сервером, а
  не ручными выгрузками.

Когда MCP не нужен: разовая обработка файлов в сессии, источники —
файлы, внутренние системы в контуре отсутствуют. Не вводи MCP «для
солидности».

Если клиент не может поднять MCP — фиксируй fallback явно в решении
(кейс declined PRODZAKAZ-1: вопрос «что если у клиента нет возможности
поднять MCP?» остался без ответа — заявка отклонена). Fallback — файлы
в сессии (вариант 1 выше), а не имитация данных.

### Дуальность режимов: продакшен и воркспейс

Проектируй оба режима сразу (образец каталога — навыки
customer-feedback-manager: «в продакшене … через MCP …; в воркспейсе
работай с файлом»):

| Режим | Данные | Обработка |
|---|---|---|
| Продакшен у клиента | ETL-конвейер и/или MCP-коннекторы | вынесена в MCP-сервер, где обосновано |
| Воркспейс/демо | файлы, загруженные в `/session` | в теле навыка, на файлах сессии |

Ограничения harness (`Референсы/HARNESS-DESCRIPTION.md`): песочница
stateless, состояние между вызовами — только файлы в `/session`;
интеграции из `python_run` не обещать. При отключённом коннекторе —
`propose_connector` один раз, после отказа работать только с файлами
и не имитировать данные (образцы — weekly-report, pro-meetings).

### Выход этапа

Зафиксированное архитектурное решение с обоснованием отброшенных
альтернатив:

- ETL-решение: способ доставки данных + почему не остальные;
- MCP-решение: выносить/не выносить + критерии + fallback, если MCP
  недоступен клиенту;
- оба режима (продакшен и воркспейс) описаны.

При выборе MCP — переходи к сборке ТЗ на MCP-сервер навыком
`mcp-tz-builder` (`plugins/ai-implementation/skills/mcp-tz-builder/`);
техническая база — `Референсы/Руководство-MCP-интеграция.md` того же
навыка.

## 4. Анти-паттерны

| Анти-паттерн | Почему плохо | Кейс |
|---|---|---|
| «Хранилище данных» в референсах навыка (excel/json «базы» в `Референсы/`) | данные вне ландшафта клиента, мгновенно устаревают | excel-хранилище в референсе навыка |
| Обработка данных в теле навыка там, где нужен ETL/MCP | обработка не переиспользуется и не тянет объёмы | непредложенный вынос обработки в MCP |
| Детали (разметка кода, псевдокод) до архитектурных решений | декомпозиция фиксирует случайную архитектуру | — |
| Обещание интеграции без подключённого коннектора и без определённого MCP-сервера | агент имитирует данные или обещает недоступное | declined PRODZAKAZ-6 — «не определен и не предоставлен MCP сервер» |

## 5. Чек-лист прогресса проектирования

Скопируй в ответ и отмечай по мере прогресса:

```
Прогресс проектирования:

- [ ] Этап 1: задача и требования сформулированы (требования уточнены
      с ИИ, входные данные и форматы разобраны, границы MVP определены)
- [ ] Этап 2: стек и библиотеки выбраны (обоснование по критериям,
      версии учтены)
- [ ] Этап 3: ETL-решение зафиксировано (способ доставки данных +
      отклонённые альтернативы)
- [ ] Этап 3: MCP-решение зафиксировано (или обоснованно отклонено)
- [ ] Этап 3: fallback зафиксирован, если MCP недоступен клиенту
- [ ] Этап 4: архитектура приложения и декомпозиция на модули
      утверждены
- [ ] Этап 5: код генерируется с семантической разметкой, контрактами
      и стандартами логирования
```
