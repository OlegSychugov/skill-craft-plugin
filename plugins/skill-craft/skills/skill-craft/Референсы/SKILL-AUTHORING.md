## 1. Структура папки навыка

Структура папки Навыка:

```
├── SKILL.md (main instructions)
├── Структуры
    └── structure.json
├── Примеры
    └── REFERENCE.md
    └── Отчет.xlsx
```

## 2. Краткость - первый приоритет

- При запуске предварительно загружаются только метаданные (имя и
  описание) всех Skills
- Как только агент загружает Skill, каждый токен конкурирует с историей
  разговора и другим контекстом.

## 3. Соглашения об именовании

Хорошие примеры именования (герундиальная форма):

- `Проверка договора`
- `Поиск поставщиков`
- `Анализ КП`

## 4. Написание эффективных описаний

- Включайте то, что делает Skill, и общий контекст применения (для кого,
  для каких задач) — без дословных триггерных фраз
- Описание использует агентом для выбора правильного Skill из
  потенциально 100+ доступных Skills
- Описание должно предоставить достаточно деталей для агента, чтобы
  знать, когда выбрать этот Skill, в то время как остальная часть
  SKILL.md предоставляет детали реализации.
- Триггеры, анти-триггеры и неформальные сигналы — в теле SKILL.md,
  раздел «Когда использовать (триггеры)», не в description

### Примеры

- description: Извлекает текст и таблицы из файлов PDF, заполняет формы,
  объединяет документы. Для работы с PDF-файлами, формами и извлечением
  документов.
- description: Анализирует электронные таблицы Excel, создаёт сводные
  таблицы, генерирует диаграммы. Для табличных данных и файлов .xlsx.

## 6. Паттерны прогрессивного раскрытия

**Уровень 1: Метаданные (всегда загружаются)**

- Тип содержимого: Инструкции. YAML. Skill.

**Уровень 2: Инструкции (загружаются при срабатывании)**

- Тип содержимого: Инструкции. Основной текст SKILL.md содержит
  процедурные знания: рабочие процессы, лучшие практики и руководство.

**Уровень 3: Ресурсы и код (загружаются по мере необходимости)**

- Типы содержимого: Инструкции, код и ресурсы. Skills могут включать
  дополнительные материалы:

    └── structure.json

    └── REFERENCE.md

### Практическое руководство

- Держите тело SKILL.md под 500 строк для оптимальной производительности
- Разделите содержимое на отдельные файлы при приближении к этому лимиту
- Используйте паттерны ниже для эффективной организации инструкций, кода
  и ресурсов.

### Паттерн 1: Высокоуровневое руководство со ссылками

Задача: Обработка PDF. Извлеките текст с помощью pdfplumber:

```python
import pdfplumber
with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```

Агент загружает FORMS.md, REFERENCE.md или EXAMPLES.md только при
необходимости.

### Паттерн 2: Организация по доменам

Задача: Анализ данных BigQuery. Доступные наборы данных:

- **Финансы**: Доход, ARR, выставление счётов → См.
  [reference/finance.md](reference/finance.md)
- **Продажи**: Возможности, конвейер, счета → См.
  [reference/sales.md](reference/sales.md)
- **Продукт**: Использование API, функции, внедрение → См.
  [reference/product.md](reference/product.md)
- **Маркетинг**: Кампании, атрибуция, электронная почта → См.
  [reference/marketing.md](reference/marketing.md)

Быстрый поиск. Найдите специфические метрики, используя grep:

```bash
grep -i "revenue" reference/finance.md
grep -i "pipeline" reference/sales.md
grep -i "api usage" reference/product.md
```

Расширенные возможности:

- **Заполнение форм**: См. [FORMS.md](FORMS.md) для полного руководства
- **Справка по API**: См. [REFERENCE.md](REFERENCE.md) для всех методов
- **Примеры**: См. [EXAMPLES.md](EXAMPLES.md) для распространённых

Для Skills с несколькими доменами организуйте содержимое по доменам,
чтобы избежать загрузки нерелевантного контекста. Когда пользователь
спрашивает о метриках продаж, агенту нужно только прочитать схемы,
связанные с продажами, а не данные финансов или маркетинга. Это держит
использование токенов низким и контекст сосредоточенным.

## 9. Рабочие процессы и циклы обратной связи

### Используйте рабочие процессы для сложных задач

Пример 1: Рабочий процесс синтеза исследований (для Навыков без кода).

**Рабочий процесс синтеза исследований**

Скопируйте этот контрольный список и отслеживайте ваш прогресс:

Прогресс исследования:

- [ ] Шаг 1: Прочитайте все исходные документы
- [ ] Шаг 2: Определите ключевые темы
- [ ] Шаг 3: Перекрёстно ссылайтесь на утверждения
- [ ] Шаг 4: Создайте структурированное резюме
- [ ] Шаг 5: Проверьте цитирования

**Шаг 1: Прочитайте все исходные документы**
Просмотрите каждый документ в директории `sources/`. Отметьте основные
аргументы и подтверждающие доказательства.

**Шаг 2: Определите ключевые темы**
Ищите паттерны по источникам. Какие темы повторяются? Где источники
согласны или не согласны?

**Шаг 3: Перекрёстно ссылайтесь на утверждения**
Для каждого основного утверждения проверьте, что оно появляется в
исходном материале. Отметьте, какой источник поддерживает каждый пункт.

**Шаг 4: Создайте структурированное резюме**
Организуйте результаты по темам. Включите:

- Основное утверждение
- Подтверждающие доказательства из источников
- Конфликтующие точки зрения (если есть)

**Шаг 5: Проверьте цитирования**
Проверьте, что каждое утверждение ссылается на правильный исходный
документ. Если цитирования неполные, вернитесь к Шагу 3.

Вывод: Ясные шаги предотвращают пропуск Claude критических проверок
валидации. Контрольный список помогает как Claude, так и вам отслеживать
прогресс через многошаговые рабочие процессы.

## Локальное дополнение: образцы и специфика каталога cowork_hub

> **Источник:** рабочие правила переработки этой области. Не часть
> присланного текста — каталог-специфика поверх стандарта.

### Конвенция папки: `Референсы/`

В каталоге `cowork_hub/` дополнительные материалы навыка кладутся в
подпапку `Референсы/` — она играет роль папок `Структуры/` и `Примеры/`
из присланного текста. Конвенция каталога не меняется:

```
skills/<alias>/
  SKILL.md          # инструкции
  Референсы/
    <справочник>.md # структуры, шаблоны, примеры
```

### Канон YAML-заголовка

`description` — одна plain-строка: без блоков `|-`/`>`, без кавычек и
«: » (двоеточие+пробел); перечисления — через «—», не «: »; `name` —
одна строка без «: »; `tags` — slug-теги без
пробелов (многословные — через дефис). Тот же канон для `plugin.yaml`,
`commands/*.md`, `agents/*.md`. Полное правило и канонический образец —
`Референсы/METHODOLOGY.md`, раздел «Локальное дополнение: валидный
YAML-заголовок (frontmatter)».

### Ограничения окружения платформы (harness)

**Правило приоритета:** при конфликте примеров дословного стандарта
(например, matplotlib-паттерны, `include_charts=True` в шаблоне отчёта) с
возможностями окружения платформы — приоритет у ограничений harness.

Выжимка ключевых ограничений:

- stateless-песочница: каждый вызов — свежий `python3`; состояние — файлы
  в `/session`; лимит одного вызова — 120 секунд;
- `/workspace` — read-only; писать только в `/session`;
- `pip install` недоступен; интернет из `python_run` недоступен, но у
  агента могут быть активированы веб-инструменты `web`/`webfetch` — тогда
  используй их согласно `Референсы/HARNESS-DESCRIPTION.md` (раздел 3.4);
  нет OCR (`pytesseract`), нет `reportlab`/`weasyprint`;
- gated-инструменты активируются вызовом `skills(skill_name="sys-...")`
  до конца сессии;
- `python_run` — последнее средство, не замена системным навыкам;
  удаление файлов — только `files(op="delete")`;
- графики для пользователя — `sys-infographics`; сканы PDF —
  `pdf(op="render")` (vision-канал);
- аргументы slash-команд — русские `${имя}` в `instructions`;
- HITL: `question` (1–3 вопроса с options), `permission` — только для
  деструктивного в `python_run`.

Полный справочник — `Референсы/HARNESS-DESCRIPTION.md`.

### Специфика плагинов

- `plugin.yaml` — тот же стандарт description: что делает плагин + когда
  использовать, без деталей реализации. `description` — одна plain-строка
  по канону (без `|-`, кавычек и «: »); `tags` — slug без пробелов,
  согласованы с навыками плагина.
- `commands/<alias>.md` — короткий запуск с подстановкой `${аргумент}`;
  детали — в навыках, не в команде. Образец: `screen-resumes.md`
  (6 строк).
- `agents/<alias>.md` — `skills` в заголовке ссылается только на навыки
  этого же плагина; в теле — роль и распределение навыков по фазам.
  Образец: `hr-recruiter.md`.
- `README.md` — отображается в витрине как описание плагина: писать
  пользовательски — назначение, состав компонентов, примеры запросов;
  не внутренняя техзаписка.
- Итоговая клиентская страница `Демо/ИИ_агент_<имя>.html` — по запросу
  пользователя, стандарт — `Референсы/AGENT-HTML.md`. При сборке плагина
  HTML-страница в корне не создаётся (требование `agent.html` отменено
  2026-10-01).
- Вынос тяжёлого контента: код (`.py`), профили (`.json`), демо-данные
  (`.csv`) — отдельными файлами, не встраиваются в SKILL.md; SKILL.md
  ссылается на них на один уровень глубины. Инструкция допускает
  дополнительные файлы рядом с SKILL.md (`reference.md`, `examples.md`,
  csv, конфиги) — конвенция каталога кладёт их в `Референсы/` поверх
  инструкции (закрепляет решение валидатора по `document-manager` /
  `digital-sales-director`).
- Тестовые и демо-данные («Данные агента …») — синтетические, по правилам
  `Референсы/DEMO-VIDEO.md` §2.3: одна легенда, деловые нейтральные
  названия (без «Ромашек», заглушек, реальных брендов и ФИО),
  неокруглённые суммы, сходящиеся итоги. Эти же данные попадают в
  клиентское демо.
- Промежуточные файлы навыка (`.pkl`, кэши, временные `.json`/`.csv`) не
  остаются в документах сессии: инструкция удаляет их через `sys-files`
  перед финальным ответом — пользователь видит только результат.
